# Changelog

What changed for people who use Airlock, newest first. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Every pull request that changes behavior adds a line under **Unreleased**.
A release moves those lines under a version heading. See `docs/releasing.md`.

## [Unreleased]

### Added
- **A Create a Raydium pool template**, on devnet. It creates two tokens, mints a supply of each to the wallet in use, and opens a Raydium constant-product pool between them, depositing the amounts you give. You type the supply and the deposit in each token's own units. The pool lines the two mints up by address, so you do not have to, and its address is worked out from the fee tier and the mints. Devnet's fee-tier config 0 is filled in until you change it.
- **An Upgrade a program template.** It deploys the build in a buffer to a program, sending the buffer's lamports where you say. Two boxes add to the same transaction: **Update its IDL** copies the IDL a `program-metadata` buffer holds into the program's IDL account and closes the buffer, and **Update its verified build** rewrites the record `solana-verify` keeps of the repository, commit and build arguments. The program data account and the IDL account are worked out from the program. It can be used on mainnet and devnet.
- **Names and symbols for classic tokens.** The **Add a name and symbol to a token** template gives a Token program token a name, a symbol and a link with Metaplex Token Metadata, where wallets and explorers look for them, and **Create a token** can add them as it makes the mint. On mainnet.
- **Create an NFT** makes an NFT on Metaplex Token Metadata, the classic standard: one token in your wallet, with its name, link, royalty and, if you like, the collection it claims. On mainnet.
- **Core NFTs and collections.** **Create a Core NFT** and **Create a Core collection** make them on Metaplex Core, with the NFT added to a collection of yours if you choose. On mainnet and devnet.
- **Compressed NFTs.** **Create a compressed NFT tree** makes a Bubblegum tree, its size chosen from the ones the programs accept and its rent read from the node, and **Mint a compressed NFT** mints into it. On mainnet and devnet.
- **Create a vesting or payment stream** locks tokens with Streamflow and unlocks them to a recipient on a schedule, amounts typed in the token's own units. On mainnet.
- **Stake with Marinade.** Four templates: **Stake SOL with Marinade**, **Unstake mSOL now**, **Unstake mSOL in a few days** and **Claim a Marinade unstake ticket**. On mainnet.
- **Build fills more fields.** A struct inside a list or an option is typed as JSON, an enum whose choices hold values by its name or as JSON, and a fixed-size name such as Streamflow's as text, so instructions that hold one, such as Bubblegum's mints, can be built.
- **Build fills arguments that hold several fields, and lists.** An argument made of fields, such as the verify program's build record, is asked for one field at a time, and a list is typed as JSON, `["--library-name", "my_program"]`, or left blank for none.
- **Templates on Build.** **Templates**, at the top of Build, opens a list of ready-made transactions beside a reader for the one you pick, as Programs reads an IDL: its questions, every instruction it writes with every field and where each value comes from, and its file as text, with Copy. The shipped ones are **Create a token**, **Create a Token-2022 token** (with a name and symbol, a transfer fee, a close authority, a permanent delegate, non-transferable tokens or a first supply, each a box to tick) and **Mint tokens**. **Use this template** opens it; with nothing on Build, the same templates are listed under the instructions to open at once. A template asks a few questions and writes the instructions for you; the new mint's key is made on this device. Everything it fills in itself is listed under **Fixed by this template** and **Worked out**, and Review and Sign reads the transaction as it reads any other, naming only the template it came from, under its title. Rent is read from your node; in Airlock Offline you type it. **Show as blocks** turns a filled template into ordinary instructions to change further.
- **Your own templates.** **Save as template**, beside Clear on Build, keeps the instructions on Build as a template: give it a name, and for each field keep its value, ask for it each time, or use the wallet in use or the fee payer. Fields you ask for that hold the same value become one question, and a key made on Build for a new account is made again each time. Your templates are listed under the built-in ones as "yours", and can be exported or removed from the reader. Templates are kept on this device only.
- **Templates as text.** In the Templates dialog, **New template** opens a short example to write your own from, with comments that say what each part is; **Edit** changes one of yours, **Edit a copy** starts one of yours from any template, and **Import a template** opens a `.toml` file the same way. Beside the text, as you type, you see the questions it asks and every instruction it writes, or why it is not a template yet, with its line; whether it fits the network in use; and whether its name is taken: a built-in template's name is refused, and one of yours asks to be replaced. **Save** keeps the text exactly as you typed it, comments and all, and changing the name of one of yours renames it. Leaving with changes not saved asks first. A file that holds control characters or the invisible characters that change the direction of text is refused, naming its line. On a phone, where there is no file picker, a template goes between devices as text: Copy it from its Text tab and paste it into New template.

### Changed
- **Review and Sign says when an instruction carries more data than its IDL describes**, and shows those bytes. An IDL describes an instruction up to its last argument; if the program has gained an argument since, the bytes after it mean something no sentence shows. Some apps pad their instructions with zeros, so the note is not an alarm, but a site's request that has one is signed from Review and Sign and not from the request window.
- **An amount set to the largest possible number reads as "the maximum"**, in sentences and fields. Lending and vault apps send that number to withdraw or repay everything, and it read as a withdrawal of 18,446,744,073,709.551615 tokens.
- **Creating a Raydium constant-product pool fills in the pool address** from the fee tier and the two mints, on mainnet and devnet. The program checks that address, so the field no longer has to be typed.
- **A program upgrade, or a change of who can upgrade a program, no longer gets a warning line of its own** on Review and Sign, in the browser request modal or under **Stored on chain**: the instruction itself already says it in a sentence. It is still signed from Review and Sign, not from the modal, and the modal says so.
- **Build takes amounts in the unit the program shows them in.** A SOL transfer's amount reads **amount · SOL** and takes 1.5, not 1500000000; a token transfer's amount takes as many decimal places as its **decimals** field, and a transfer fee is typed in percent. A value with more decimal places than its unit has, or too large for its field, is refused with a message rather than rounded or cut. An amount the app cannot scale without reading an account says it is in base units. Opening a transaction on Build from Review and Sign shows its amounts the same way. The accounts the program fills in itself, and arguments left to their default, fold under **Filled in for you**, closed, at the end of each instruction.
- **Build offers a choice where an instruction takes one of a fixed set of words.** An authority type on **setAuthority** (Token and Token-2022), the state new token accounts start in on Token-2022's default account state, a stake authority, the format of program metadata and the like were a field Build could not fill, so those instructions could not be built at all. They are now a list to pick from, and opening such a transaction on Build shows the one it holds.
- **A site's request keeps your work when something else takes Review and Sign.** Sending from Wallets, Build, Stake or anywhere else while a site's request is open there sets the request aside with any signatures already added, and the page says so. Opening the request again from its card or bar brings it back as you left it. Before, it was dropped and prepared again from scratch. A site's request no longer replaces a transaction of your own that already carries a signature without asking first.

A transaction from Build, Wallets or Stake, or one pasted or scanned, says so in the same place. While that request is on screen, its reminder card no longer shows over the page. On a phone, a request you set aside is a bar at the top of the page instead of a card at the bottom, and no toast covers an open sheet or dialog.

### Security
- Restoring a Vector XMSS wallet from its recovery phrase a second time now signs the same rotation with the same signature. Before, each restore made a new signature with the key's last leaf, and two of those could give the key away.
- An account state that claims more leaves than a key has is refused. Before, scanning one made the key unable to sign on that device.
- **An IDL read from the chain can only describe its own program.** A Codama IDL can carry other programs beside its own, and Airlock took them from any file. A site could publish an IDL for its own program that also described another one, such as the Vote program, and a later transaction of that program read in the site's words, with the site's program nowhere in it. It could take the associated-token program's wording from the Token IDL that ships, too. An IDL read from the chain now words its own program and nothing else, and a program a shipped file carries stays with that file.
- **Handing over a vote account is warned of**, like handing over a stake account: authorizing a new voter or withdrawer never gets Sign in a site's request window, and Review and Sign says what it does above the instructions. A program upgrade, or a change of who can upgrade a program, gets the same warning whenever the loader's shipped IDL is not what puts it in words.
- A small Anchor IDL can no longer make Airlock use gigabytes of memory while reading it. One generic type with many fields, used many times, is refused past a limit, and that program's instructions read raw.
- **An Anchor IDL whose generic type hands its own parameter to another is now read**, as GMX's does with its prices. Before, reading one closed the app, and since a program's IDL is read from the chain as soon as a transaction names the program, a transaction of such a program could not be reviewed at all. An IDL whose generic types hold themselves, or expand into more than a type may hold, is refused, and its instructions read raw.

### Security
- On Linux and macOS, Airlock's data folder is now only readable by you: the folder is created `0700`, so other accounts on the computer cannot read the vault, settings, site grants or logs, and the files Airlock saves are `0600`. If the list of connected sites is damaged, sites ask again and you are told. Files from an earlier version are moved the first time they are saved.

- A large address book is read a part at a time, so a public node is not asked for more than it allows: about 40 requests every 30 seconds rather than two for every address. Your wallets come first and more often, every address still comes around, and Refresh still reads them all.
- Unlocking, creating a vault and changing the password no longer hold up the window, and say they are working.
- The request modal simulates what a site asks before it offers Sign, and shows what would change. If the node says it would fail, or cannot say, Sign turns amber and the modal says why.
- The request modal and Review and Sign now say when Airlock changed a site's transaction on its own: moving it onto an offline key's durable nonce, or setting its compute limits from a simulation.
- The request modal says how many of a v0 transaction's accounts come from lookup tables.
- The request modal lists the wallets that sign if you press Sign.
- The request modal warns when a site says it is on another network than the one Airlock is on.
- The connect modal opens with the wallet you are using ticked, at the top of the list. When you tick several, it is the first one the site gets, or else the first you ticked.
- A site reloading its page finds your connection again, with no prompt, until it disconnects or the app closes. Before, it had to ask again each time. A closed app no longer shows the site an error when it checks for a connection.
- A site can only ask for a signature from accounts it is connected to. The app checks this itself now.
- Review and Sign hides its row of steps when a transaction only needs simulating and signing with keys on this device. In a batch from a site, the row of transactions stays and only the steps of the transaction on screen are hidden.
- The browser request modal offers Sign when it cannot put every instruction in words, or put some in words with an IDL read from the chain. Sign is amber then, and Review keeps the primary colour. A transaction's card in a batch reads **Sign without summary**. Before, only Review was offered.
- QR transfers are format 2: the transfer id is the first 8 bytes of the payload's SHA-256, and the receiver checks it. Both devices need this build. A code that claims a place in a transfer already filled with other bytes, or a payload that fails its checks, now starts the transfer over with a message, instead of the later code silently replacing the earlier one or the scan getting stuck on a bad payload.
- Sign fetches the blockhash when it is pressed. There is no Refresh blockhash button anymore. A transaction this app made or relays, that nothing has signed yet, is moved to a fresh blockhash on the press that signs it. Once a blockhash has expired, Sign moves any transaction off it instead of being disabled. Rebuild on a fresh blockhash is left only for an expired transaction this device has nothing left to sign. The Sign screen drops its "What you are signing" box: the steps at the top say what comes next, and they no longer show signing as held up by a blockhash Sign moves off.
- Summary no longer lists ComputeBudget instructions. A line above Signatures states the most the transaction costs in fees and who pays it. Inspect still lists those instructions and the limits they set. The instructions left keep their numbers in the transaction, the ones a failed simulation names.
- The IDLs of third-party programs (Raydium, Orca) ship as one compressed file beside the app instead of inside it, about 96 KB in place of 1.8 MB of JSON. Desktop reads it while it starts; the web app fetches it once and caches it. The app checks it against the checksum its build pinned and refuses a file that does not match, and Review and Programs say so. The IDLs of the programs the wallet itself uses stay compiled in.
- IDLs are kept per network: mainnet, devnet, testnet, and localnet for a node whose genesis is none of those. The Programs screen, review and Build read the IDLs of the cluster in use. A custom RPC reads those of the public cluster its genesis matched. An IDL imported or read from the chain on one network does not show on another, and the export carries every network. Files stored before this update are kept for the cluster in use when the app first opens.
- Raydium's CLMM and CP swap programs come with the app on mainnet too. Their files are the devnet ones with mainnet's program, admin and fee receiver addresses, which is all the two networks' published IDLs differ in. The Raydium router, Vector and the Ed25519 signer stay devnet only.
- Checking an embedded IDL online compares the chain's bytes with the document the file was made from, as well as with the file. A converted or annotated file whose source the chain still publishes shows "matches its source" instead of "differs". The Programs screen says where each embedded file came from and what was changed in it.
- A converted browser or paste request discards the site's compute unit and loaded-accounts limits when online. The rewrite is simulated at the highest of each (1,400,000 units and 64 MiB), and both limits are what it used plus 10%. The site's price per compute unit is still kept. Offline, or when the simulation fails, limits the site set are kept. Build and rebuilds that fill blank limits from a simulation use the same 10% headroom.
- A transaction rebuilt for a programmatic signer, Vector wallet or Squads vault is probed at the highest compute limit, then both the compute and loaded-accounts limits are set from that simulation plus 10%. Sign does the same again once an authorization is signed, so the inner instructions are measured and the limits on screen (and on the wire that is signed) match what the node used. Once a signature over the transaction itself is in place, those limits are left alone so fitting cannot void it.
- A Squads rebuild no longer drops execute because a static compute estimate (the site's limit plus wrap overhead) was above 1,400,000. The wrap caps at the network maximum and the real use is taken from simulation, so a stacked estimate like 1,500,000 no longer stops a proposal that would fit.
- Signing an authorization (a programmatic signer's or a Vector account's) is a press of its own. Sign then simulates the authorized transaction and fits its limits before the next press signs the transaction, so an authorization made on this device no longer lands out of compute. The browser's quick Sign is not offered when this device signs an authorization: Review does it. A simulation that fails, as it does before an authorization is signed, keeps compute at the highest limit instead of the little the failed run used.
- Share opens on Everything, now its first tab. Its Signatures tab has tabs of its own: Local, which it opens on, puts the signatures made by keys on this device in one transfer; All puts every signature in one transfer; Individual shows a code for each.

### Fixed
- Review reads a Raydium CP swap pool created with a creator fee (`initializeV2`, new on mainnet and devnet) like any other new pool, with the creator fee it sets. Before, that instruction showed as unread.
- The camera preview on Windows is no longer black. With WebView2 156 the camera stopped as soon as it started, and a scanner canvas hid the video. On macOS the bundled apps had no camera at all, since the bundle left out the camera description macOS asks for. They have it now, and a window without a camera says why rather than asking you to open the app in a browser.
- A signature scanned or pasted on Review and Sign that completes a site's transaction now sends it back to the site. Before, a request whose last signature came from another device was never answered.
- A site's request that names a program with a large IDL no longer freezes the window while it is read. Reading now happens away from the window, and says so. If it takes more than 4 seconds, the transaction is shown as its programs and bytes rather than in words, and Sign is offered only as it is for anything unread.
- A node that says it is getting too many requests now stops the background read, and the sync status and notices say so. Before, Airlock went on asking and showed "Synced". What was read before it stopped is kept, and the next read goes on from there.
- Addresses a node refuses to read are now reported, in a notice and on Refresh, rather than quietly left as they were.
- The sync status on the network chip now tells of any background job that failed, not only the balances.
- What comes back late from the node no longer changes what is on Review and Sign. A simulation could put back the transaction you had just replaced, or take a signature off the one on screen. A new blockhash or a Submit could overwrite or clear what had taken its place. Of two transactions pasted one after the other, the last is now the one that stays.
- A Sign press that first asks for the vault's password no longer signs whatever is on the screen once you unlock. It signs what you pressed it on, and nothing if that has been replaced.
- A press that moves a transaction to a new blockhash and then fails to sign no longer leaves the countdown on the new blockhash's expiry.
- Airlock now starts when something else holds its connection to the browser, and the Extension chip says what is wrong. It used to wait for ever with no window if that something did not answer, and close without a word if it hung up.
- A transaction is no longer reported as rejected, to you or to a site, when the node simply did not answer. It may have gone through, and a site told it had failed could have sent the same thing again. Airlock now keeps following it, and its toast says what became of it. A site gets the signature if it is seen within 90 seconds, and otherwise a new `send_unknown` error. Sign says it may still land, and keeps the transaction on screen so that you can send it again, which is safe.
- A send approved near the end of the ten minutes a request waits is no longer reported to the site as expired while it is going out. The site now gets its result, however long that takes.
- When a node stops answering while a site's send waits for the commitment it asked for, the wait now ends after about 90 seconds. Before, a read that timed out counted as one second of the wait, and the site was told the request had expired.
- A request's modal now closes by itself when the page that asked closes, or the browser does. Before, it stayed for up to ten minutes. Approving it answered nobody, and a transaction to send still went out.
- When Airlock closes, a site waiting on it hears straight away. Before, it could wait out the full ten minutes.
- A damaged `vault.json` no longer locks you out while a good copy sits beside it. Unlocking opens the copy kept before the last save, keeps the damaged file as `vault.json.unreadable`, and tells you the last change to the vault may be missing.
- A request waiting in the app no longer holds up other requests from the same browser. A site reloading while a modal was open, for one, waited until that modal was answered.
- A browser request that expired unanswered could stop that browser's connection to the app.
- A page left open for a while could lose its connection to the extension and fail its next request.
- The embedded IDL files have LF line endings on every checkout, so their checksums no longer depend on the OS the app was built on. A Windows build and a Linux or web build pinned different checksums for the same embedded IDL.
- A browser or paste request whose programs create accounts from new keypairs in their own calls, like Orca's pool creation creating its two vaults, no longer converts into signer slots nobody can sign. When the transaction's own instructions do not explain an unsigned outside signer, it is simulated and the accounts its programs create count as one-time keys, left for the site to sign or replaced by keys made here. Without a node, or when the simulation fails, only the transaction's own instructions count, as before.
- Review and Sign simulates a legacy or v0 transaction it signs as it came, instead of saying it could not simulate because the transaction is not v1.
- Submit on Review and Sign sends a legacy or v0 transaction as it is. It used to refuse with "payload is not a Solana transaction v1 (expected 0x81 prefix)".
- A transaction that went back to a site from Review and Sign is not sent twice. The site may send it itself, so Submit waits up to 10 seconds while the app watches for it on chain. If it lands, a toast says the site sent it and follows it to confirmed, and Submit stays off. If it does not, a toast says the site did not send it, and Submit turns on. In a batch, each transaction is watched for on its own.

### Security
- The app's window now loads only the app's own files, runs no script written into its page, and cannot be replaced by another page. It also blocks the usual ways a page sends something out, though not all of them: `docs/browser-bridge.md` lists what is left.
- The password of a vault is far more expensive to guess from a copy of its file: deriving its key now takes 256 MiB and three passes, rather than 19 MiB and two. A vault you already have moves to the new cost the next time you unlock it, and so does the backup beside it. A copy made before then stays at the old cost.
- A new vault or a new password has to be at least 12 characters, and cannot be made of common words or patterns. A password you already have keeps working.
- Approving or running a Squads proposal, or voting on a Realms proposal, signs something stored on chain rather than what it does. Airlock now says so, and the request modal no longer offers one-click Sign for it. Online, Review and Sign shows what the node says the proposal holds. On a device with no network, Sign waits until you tick that you have checked it somewhere you trust, and any contents the other device sends in the context note are marked as something it cannot check.
- A transaction that hands over control of something no longer gets one-click Sign in the request modal, however well it reads: a token approval or change of authority, giving an account to a program, handing over a stake account or durable nonce, or changing a program. The modal and Review and Sign say what it does, and you sign it from Review.
- A site connected to one wallet can no longer ask another wallet of this device to sign. Only the account it named was checked, not who the transaction asks to sign, so a press could have used a wallet the site was never given. Now such a request is refused.
- The buttons that approve a request stay off for a moment after they could first be pressed, so a click meant for something else cannot land on one as a site's request appears.
- A transaction signed on Review and Sign can no longer go to the wrong site. If a site's request was opened on the screen while a signature was being made, that site was sent the transaction signed for what was there before, and the screen went back to it. Now a signature for something no longer on the screen is not used.
- The extension's host, and a second launch of Airlock, now check that the local connection they reach is yours. Another account on the same computer could create it before Airlock did, hear what every site asked, and answer in Airlock's place.
- An error from your node no longer tells a site the address of the node, which can hold an API key. A send that failed for want of a connection could hand it over. It no longer reaches the notices or the logs either.
- A site can no longer flood Airlock with requests. One site can ask at most 30 times every 10 seconds and keep 8 requests waiting, and 32 can wait in all. A page you have not used yet can no longer open a connect or sign-in modal.
- One oversized request from a site could leave the extension unable to reach Airlock, for every site, until the browser or Airlock restarted. The extension now refuses a request that large, and if the bridge ever does stop, the next request starts it again.
- A sandboxed frame can no longer ask in the name of the site that hosts it. It was given that site's origin, and with it the site's connection.
- A site's request id no longer reaches the app, so a site can no longer choose the code shown beside its request.
- However many requests a site makes, they can no longer push a transaction out of the notifications, whether it has ended or is still being watched.
- The record of used signing leaves (`vector-leaves.json`) is written so that a power cut on Windows cannot undo it after a leaf has signed. It also keeps no older copy, which could have been read in its place and let a leaf sign twice. Every other file's save is flushed the same way.
- A context note can no longer use up an XMSS key's leaves by naming a high floor. The device that holds the key refuses a floor above its own count, and says to scan the account state if the other device is right.
- A site can no longer get a Vector authorization by asking for a signed message. A message of exactly 32 bytes was refused only if it did not read as text, and a site that builds the transaction can vary it until the digest does. Now every 32-byte message is refused, unless it is all hex digits, as a nonce often is.
- A message or sign-in holding characters that hide or reorder text, such as a right-to-left override, no longer shows as text. A message shows in hex with a warning, and a sign-in is refused.
- A key or seed phrase on Add wallet is wiped from the screen and from memory however the vault locks. Before, only the lock button in the top bar did that: when the vault locked by itself, or from the tray, a new seed phrase stayed on screen and in memory.
- A vault whose file could not be read for a moment was taken for no vault at all, and Airlock offered to create a new one over it. Doing so, then saving once more, destroyed the real vault. Airlock now says the file could not be read, offers to unlock, which tries the file again, and refuses to create a vault over a file that exists or cannot be read.
- An IDL read from the chain can no longer crash or freeze Airlock. A type that linked to itself ended the app as soon as a transaction named its program, types that each named the next one twice froze the app for minutes or more, and a long list of empty items could use all its memory. Airlock now shows such an instruction undecoded. Any program's author could publish one, and a connected site only had to send a transaction naming the program.
- More secrets are wiped from memory once used: the seeds a Vector wallet's key is rebuilt from, the seeds and normalized words of a recovery phrase (BIP-39 mnemonics now wipe themselves), the words on the add-Vector-wallet form when it closes, and the password field after a failed unlock as well as a successful one.
- On desktop, when none of `AIRLOCK_DATA_DIR` (or `AIRLOCK_OFFLINE_DATA_DIR`), `LOCALAPPDATA`, `XDG_DATA_HOME` and `HOME` is set, the app refuses to start and says so. Before, it kept its vault and its record of used signing leaves in whatever folder it was started from, so a second launch from elsewhere had neither. The native host then keeps no log instead.
- XMSS, Winternitz and Falcon-512 seeds, and the salts of hash-based signatures, are drawn from the OS on each use instead of a generator the OS seeded once per thread, so a forked process or a restored VM snapshot cannot repeat them.
- An XMSS or Winternitz key signs only the digest its leaf and salt were recorded for. When the transaction changed between recording and signing, nothing is signed. Before, a Winternitz key would have signed the new digest with the salt recorded for the old one, giving the key away.
- An account state that shows an XMSS account on a key of its phrase other than the next one this device made, further on or one it had moved past, now marks the wallet restored, so it signs only a move to its next key, at its last leaf. Before, the device went on signing with that key from the floor it was told, and leaves another copy of the phrase had used could sign twice.
- Rotate key on an XMSS wallet keeps the signatures it makes, and pressing it again shows them instead of signing again. Before, each press spent another leaf per nonce, which could use up a key near its end, and a wallet restored from its recovery phrase had one try: if that QR was lost, its key could not rotate.
- An XMSS key past 95% of its leaves signs only a move to its next key, on the device that holds it as well as in the rebuild. Before, a context note naming a leaf floor near the end, or a key that signed many transactions that never landed, could make it sign its last leaf on something else, and it could then never rotate. A transaction that hands the account to a key this device did not make is now refused before a leaf is recorded, and a context note can no longer change the scheme of an account whose wallet is on this device or that a rebuild read.
- A record of used signing leaves (`vector-leaves.json`) that cannot be read now stops XMSS and Winternitz keys from signing, and the file is left as it is. Before, it was set aside and the record started empty, falling back on the vault's counter plus 16 leaves.
- Airlock and Airlock Offline lock their data folder while they run, and a second copy of either refuses to start with a message saying why. Before, two windows of Airlock Offline could run on one vault: each kept its own copy of the vault and of the record of used XMSS leaves and saved over the other's, so a leaf could sign twice. The online app was held to one copy only by its bridge socket, and not at all when the socket could not be named.
- Secp256k1 and EIP-191 Vector keys sign with k256 0.14, off crypto-bigint 0.5 and its timing advisory (RUSTSEC-2026-0387). crypto-bigint 0.7 is at 0.7.9, off the yanked 0.7.7.
